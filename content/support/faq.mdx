# FAQ

## Is recv.fund custodial?

No. recv.fund is software you run on your own server. Nothing we run is in the path of a payment. Funds move from the customer through the on-chain program to the settlement wallet you registered, or sit at a deposit address until your install sweeps them to that wallet.

The program can move funds only to a merchant's registered settlement wallet and to the fee collector. No instruction takes a caller-supplied destination. Only a transaction signed by your admin wallet can change your settlement wallet. There is no pause or freeze function, and the vendor authority cannot call the sweep instructions.

recv.fund is non-custodial software; you remain responsible for your own legal obligations in your jurisdiction.

## What fee is charged, and where is it enforced?

A percentage of each settlement, deducted by the on-chain program and sent to the fee collector in the same transaction as the settlement. There are two rates, one for checkout payments and one for sweeps, both stored in the program's configuration in basis points. The rates in force are read from the program and shown in the dashboard when the program address is configured, before you register.

- Checkout payment: the fee is taken at payment time. The settlement is two transfers in one transaction: the merchant share to your settlement wallet and the fee to the fee collector.
- Deposit and sweep: nothing is taken when the deposit arrives. The fee is taken when the balance is swept to the settlement wallet.

There is no subscription and no setup fee. You pay for your own server and the network fees of sweeps and payouts.

## Can the fee change?

Within a limit. The program has a hard maximum of 200 basis points (2%) compiled into its code. recv.fund can lower or raise a rate below that limit without a program upgrade. The program rejects any rate above it.

On Robinhood Chain the contract is not upgradeable; any change would be a new deployment with a new address, and merchants would need to register again. On Solana the upgrade authority is to be burned or moved to a multisig before mainnet use; until that is published, treat the deployment as provisional.

## What happens if my server is offline?

Payments still settle. A checkout payment goes from the customer's wallet through the program to your settlement wallet whether or not your server is running. A deposit lands at the customer's deposit address in the same way.

What stops is bookkeeping. When the server is back:

- The program-event watcher resumes from its saved position and credits every checkout payment it missed.
- The deposit watcher resumes from its per-address progress and credits every deposit it missed.
- Detected transfers continue counting confirmations.
- Queued webhooks and queued sweeps and payouts resume; a webhook whose delivery lease expired is retried.

Both watchers keep their position in the database and advance it only after a page has been fully processed, so a crash mid-page replays that page safely. The RPC nodes you use must retain enough history for the catch-up. Payments whose expiry passed while the server was down are cancelled by the expiry scheduler. A checkout payment made for such a payment is still credited to it when discovered and can move it to a filled state; see the expiry question below for deposits.

If a payment is still missing afterwards, report its transaction hash under Payments, Missed payments.

## What if I lose the AES key?

`AES_ENCRYPTION_KEY` in `/opt/recvfund/.env` encrypts every secret in the database: hot wallet private keys, webhook secrets, the SMTP password and the session signing secrets. Without it those secrets cannot be recovered and there is no key export.

Deposit addresses and settlement are not affected, because no deposit key exists and the settlement wallet is yours. Funds at deposit addresses can still be swept: create a new hot wallet, assign it to the project, and update the sweeper on-chain with your admin wallet. Back up `.env` together with the database; see [What to back up](/deployment-guide/introduction/).

## Can I change the settlement wallet?

Yes. Under Wallets, Deposit wallets, prepare a settlement update for the registration. The server returns an unsigned transaction; you sign it with the admin wallet that registered, and the server confirms it on-chain. Only the admin wallet can do this. Deposit addresses do not change, because they are derived from the merchant id and the customer reference, not from the settlement wallet.

## What if a customer underpays or overpays?

The payment is valued at the confirmed amount received.

- Below the requested amount by more than the fill tolerance (0.01 USD by default): `PARTIALLY_FILLED`. A later deposit from the same customer is matched to it and can bring it to `FILLED`. Partially filled payments do not expire automatically.
- Within the tolerance: `FILLED`.
- Above the tolerance: `OVER_FILLED`. The whole amount is credited and reaches your settlement wallet; nothing is returned automatically.

Each state is sent once as a webhook. The checkout page asks for an exact token amount from a quote and states the currency and network; funds sent in another currency or on another network are not credited to that payment.

## What happens when a payment expires?

An `OPEN` payment past its expiry (24 hours by default) becomes `CANCELLED` and a `payment.cancelled` webhook is sent. The checkout page no longer offers a quote or a wallet payment for it.

Funds can still arrive afterwards. A checkout payment for that invoice id, or a transfer that was already detected before cancellation, is credited to the cancelled payment and can move it to a filled state. A new deposit to the customer's address after cancellation is not matched to a cancelled payment; it is credited to the customer's newest open payment if there is one, or recorded as an unmatched deposit under the customer. Unmatched deposits are swept like any other balance.

## How do refunds work?

There is no refund feature. Checkout payments arrive in your settlement wallet, which the server does not control, and deposits arrive at addresses that have no key.

If you decide to return funds, the mechanism the software provides is a payout: fund the project's hot wallet with the token, then create a payout to the customer's address from the dashboard or the API. Payouts are subject to the project's limits and approval. See [Payouts](/features/payouts/).

## Is there KYC?

No identity verification is built in, and there is no account with recv.fund. Merchants remain responsible for their own legal obligations, including any customer verification their jurisdiction requires.

## Which wallets work on the checkout page?

Injected browser wallets: EVM wallets on Robinhood Chain and Phantom- or Solflare-compatible wallets on Solana. WalletConnect is not implemented yet, and neither is EIP-2612 `permit` (ERC-20 payments use an approval step followed by the payment).

Customers without a browser wallet, or paying from an exchange, send to the deposit address shown on the page or in its QR code. The QR code contains the address; the customer must use the currency and network stated on the page.

## Is testnet supported?

Yes. Install with `--testnet` and the install runs against Solana devnet and Robinhood Chain testnet with the test tokens listed in [Networks and tokens](/support/networks/). Every payment on such an install is a test payment: the checkout page labels it and the checkout URL carries `test=true`. Use a testnet install first.

## Can I switch between mainnet and testnet?

No. The network type is written to `.env` at install time and every chain, currency, registration and address belongs to it. Changing it requires a reset, which removes the containers, images and data. Run a second install on another server for the other network.

## How do I update?

```bash
bash <(curl -fsSL https://recv.fund/install.sh) --update
```

The script pulls the latest images, runs database migrations against the new image and then swaps the containers. The API refuses to start with unapplied migrations, which is why migrations run first. The same operation is option 2 in the script's menu. See [Script usage](/deployment-guide/script-usage/).

## How do I back up?

Three things:

1. The database. With the bundled Postgres: `docker compose -p recvfund exec postgres pg_dump -U recv recv > backup.sql` from `/opt/recvfund`. With an external Postgres, use its own backup.
2. The `api-uploads` volume, which holds project logos.
3. `/opt/recvfund/.env`, in particular `AES_ENCRYPTION_KEY`.

Restore is the reverse. See [What to back up](/deployment-guide/introduction/).

## What if the hot wallet runs out of native coin?

Sweeps and payouts need SOL or ETH for network fees. A sweep or payout that cannot be funded fails before it is signed and is shown as failed with the reason; nothing is broadcast. Top up the hot wallet and queue the sweep again or create the payout again. There is no low-balance alert in this release, so check the balance under Wallets, Hot wallets.

## Is a transfer straight to my settlement wallet credited?

No. The watchers credit two kinds of transfer only: program events for checkout payments, and transfers into deposit addresses. A customer must pay through the checkout page or send to their deposit address.
